# SecureCode AI Architecture

## Current milestone

The current vertical slice accepts one Python source file, runs Bandit static analysis, persists normalized findings, and displays the completed scan findings. No source code is executed.

## Scan pipeline

```text
Upload
  |
  v
Upload validation and UUID temporary storage
  |
  v
Scan record: queued
  |
  v
Scanner service: running
  |
  v
SecurityScanner interface
  |
  v
Bandit adapter
  |
  v
Bandit JSON output
  |
  v
Dedicated Bandit parser
  |
  v
Normalized ScannerFinding objects
  |
  v
Finding repository
  |
  v
PostgreSQL-compatible Scan/Finding tables
  |
  v
Scan counts and status: completed
  |
  v
Temporary file cleanup
  |
  v
Frontend findings dashboard
  |
  v
Deterministic CWE/OWASP enrichment
  |
  v
Structured analysis provider
  |
  v
Persisted developer-review analysis
```

If Bandit cannot produce usable JSON, the scan is marked `failed` and the temporary file is still removed.

## Components

### Upload route and service

`POST /api/scans` accepts a multipart field named `file`. The route delegates to `upload_service.py`, which validates the filename and extension, rejects empty uploads, streams at most the configured upload size, writes a UUID-generated `.py` path in the application temporary directory, creates the queued Scan, runs the scanner synchronously, and removes the temporary file in all outcomes.

The original filename is stored as `Scan.name` metadata. It is never used as a filesystem path. The service does not import, execute, evaluate, or dynamically load the uploaded source.

### Scanner abstraction

`SecurityScanner` defines the scanner contract. `BanditScanner` is the only implementation currently present. Future scanners can implement the same contract without making the scan service depend on their output format.

`ScannerResult` contains normalized `ScannerFinding` objects, scanner errors, and metadata. The domain persistence model is populated from normalized objects rather than Bandit's JSON structure.

### Bandit execution

Bandit runs with:

```text
[sys.executable, "-m", "bandit", "-f", "json", target_path]
```

The invocation uses `shell=False`, `stdin=DEVNULL`, captured stdout/stderr, `check=False`, and a configurable timeout (`SCANNER_TIMEOUT_SECONDS`, 30 seconds by default). The target path is generated by the server and is passed as one argument.

Bandit's non-zero exit code is not automatically treated as a scanner failure. Valid JSON is parsed and persisted even when findings make Bandit return non-zero. A scan fails only when output is absent, malformed, or contains invalid finding data, or when process startup/timeout fails.

### Normalization

Bandit's `issue_severity` and `issue_confidence` values are mapped directly to the existing application enums:

- Bandit `LOW`, `MEDIUM`, `HIGH` map to the same application values.
- Bandit has no `CRITICAL` category, so no critical findings are fabricated.
- Bandit `HIGH`, `MEDIUM`, and `LOW` confidence values map directly.
- `issue_text` is used as the finding title and description because Bandit's JSON does not provide a separate description field.
- Original Bandit finding JSON is retained in `raw_metadata`.

The stored file path is the original scan filename, not the internal temporary path.

### Persistence and API

The scanner service uses the existing repositories to bulk-create findings, count normalized severities, update Scan counters, and transition status. It does not issue raw SQL. The routes expose:

```text
GET /api/scans/{scan_id}
GET /api/scans/{scan_id}/findings
```

These return Pydantic response models rather than ORM objects directly.

The Docker Compose stack contains PostgreSQL, the migration-running FastAPI backend, and the Next.js frontend. The backend waits for PostgreSQL health before applying migrations and starting.

### AI analysis boundary

`LLMProvider` is provider-independent. The current `MockSecurityProvider` is local and deterministic. `analysis_service.py` supplies targeted finding context, validates the structured response, persists it separately from `Finding`, and never applies generated code. Generated diffs are review artifacts only.

## Security boundaries

- Uploaded source is untrusted data.
- No uploaded Python is imported or executed.
- No package manager, build script, setup script, or uploaded shell command is run.
- No scanner subprocess uses shell string concatenation.
- Bandit stderr and internal exception details are logged server-side only and are not returned to clients.
- Temporary files are removed after successful scans, findings-reported scans, malformed output, timeout, process failure, database failure, and unexpected errors.
- Backend credentials remain environment-only and are never exposed to Next.js.

## Testing architecture

The production database remains PostgreSQL. When Docker/PostgreSQL is unavailable, automated repository and integration tests use isolated SQLite fixtures only; they do not alter the application production URL. Bandit tests execute the installed Bandit package for real and separately mock malformed output, timeout, and missing-process conditions.

## Scope boundary

The current frontend provides upload, service status with health retry, persisted finding retrieval with retry, severity filtering, classification details, source snippets, and review-only mock analysis. Additional scanners, RAG, Git integration, authentication, queues, and CI/CD are not part of the current implementation.
